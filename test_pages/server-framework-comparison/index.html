$Server Framework Comparison

Express · Fastify · Hono · Koa · Elysia · NestJS의 특징과 장단점을 한 표로 비교하고, 이 머신에서 직접 잰 HTTP 처리량을 함께 싣습니다.

02 · 프레임워크별특징과 장단점

Express

Node.js의 사실상 표준인 최소주의 웹 프레임워크. 여섯 중 생태계와 레퍼런스가 가장 큽니다.

최신 안정 5.3.0 (2026-10-09) 4.x 병행 (latest-4 4.22.3) stars 약 69.7k (2026-11-20)

핵심 특징

  • connect 스타일 (req, res, next) 미들웨어 체인
  • 5.x부터 async 핸들러가 reject되면 라우터가 에러로 처리 (Promise 지원)
  • 라우팅을 path-to-regexp 8.x로 갱신하고 정규식 sub-expression 패턴을 제거 (ReDoS 완화)
  • 템플릿 엔진, 정적 파일, body-parser, cors, session 등 공식 미들웨어 목록 제공
  • v5는 Node.js 18 이상. Bun에서도 동작 (Hono 문서의 언급 기준)
  • 직접 의존성 28개, 패키지 자체는 약 75KB

장점

  • 가장 큰 생태계: npm 주간 다운로드 약 2억 건, stars 약 7만
  • 학습 자료와 예제를 찾기 쉬운 편 (정성적 평가)
  • 5.x에서 async 에러 처리가 자동화되어 try/catch + next(err) 보일러플레이트 감소
  • 미들웨어 모델이 단순해 서드파티 미들웨어 호환성이 높음
  • 4.x → 5.x 마이그레이션 가이드와 보안 패치 지속 (5.2.0에서 CVE-2024-51999 수정)

단점

  • 검증, 스키마, 직렬화가 내장되어 있지 않아 직접 조합해야 함
  • 타입은 @types/express 별도이고, 라우트 단위 타입 추론은 일반적으로 약한 편으로 평가됨
  • Web 표준(Fetch) 기반이 아니어서 Workers, Deno 같은 엣지 런타임에 그대로 올릴 수 없음
  • 공개 벤치마크에서 하위권 (fastify/benchmarks 2026-11-14 실행 기준 53,784 req/s)

적합한 상황 — 레퍼런스와 인력 수급이 중요하고 생태계 호환이 우선인 일반 Node.js API/서버.

GitHub · expressjs/express 공식 문서 · expressjs.com

Fastify

스키마 기반 검증·직렬화와 플러그인 캡슐화를 갖춘 저오버헤드 Node.js 프레임워크.

최신 안정 5.12.8 (2026-11-02) 차기 6.0.0-alpha.6 (pre-release) stars 약 37.5k (2026-11-20)

핵심 특징

  • JSON Schema로 라우트 검증과 응답 직렬화 (ajv, fast-json-stringify)
  • hooks / plugins / decorators와 encapsulation으로 컴포넌트 격리
  • Pino 내장 로깅
  • 타입 내장, TypeBox type provider로 스키마에서 핸들러 타입 추론
  • 라우터는 find-my-way
  • HTTP 서버 없이 요청을 주입하는 테스트용 light-my-request 포함

장점

  • 스키마 하나로 검증 + 직렬화 + 타입 추론(type provider)을 연결할 수 있음
  • 플러그인 캡슐화로 대형 앱 구조화에 유리
  • 로깅(Pino), 테스트 inject 등 서버 개발에 필요한 요소가 기본 제공
  • fastify/benchmarks에서 Node 전용 프레임워크 중 상위권 (2026-11-14: 78,696 req/s, Express 53,784)
  • 활발한 릴리스 (5.7 ~ 5.12가 2026-01 ~ 2026-08 사이 연속 릴리스)

단점

  • Node http 기반이라 엣지 런타임에 그대로 올리기는 일반적으로 어려움
  • 플러그인 캡슐화, 데코레이터, 훅 개념의 학습 비용 (Express 대비)
  • 직접 의존성 15개, 설치 크기 약 3.0MB (여섯 중 가장 큼)
  • 메이저 전환 시 breaking change 존재 (5.0.0: setDefaultRoute 제거, variadic listen 제거, 새 logger API 등)
  • 스키마 없이 쓰면 직렬화·검증의 이점이 일반적으로 줄어듦

적합한 상황 — Node.js에서 스키마 기반으로 고성능이고 구조화된 REST API를 만들 때.

GitHub · fastify/fastify 공식 문서 · fastify.dev

Hono

Web 표준만 사용하는 초경량 프레임워크. Cloudflare Workers, Deno, Bun, Node.js에서 같은 코드가 동작합니다.

최신 안정 4.13.19 (2026-11-16) 차기 5.0.0-rc.1 (pre-release) stars 약 33.0k (2026-11-20)

핵심 특징

  • Fetch API(Request/Response)만 사용
  • 라우터 5종: RegExpRouter(전체 라우트를 하나의 정규식으로), TrieRouter, SmartRouter(기본, RegExp + Trie 중 선택), LinearRouter(콜드스타트용), PatternRouter(최소 크기)
  • hono/tiny 프리셋은 14kB 미만 (공식 홈 문구)
  • 직접 의존성 0
  • 내장 미들웨어(CORS, JWT, Logger, Compress, ETag, Secure Headers 등)와 헬퍼, JSX, RPC(hc)
  • Node.js에서는 별도 어댑터를 사용

장점

  • 멀티 런타임: Cloudflare Workers, Deno, Bun, Fastly, AWS Lambda, Node.js, Vercel, WASM
  • 의존성 0, 작은 번들
  • 내장 미들웨어가 풍부 (공식 홈 문구 “batteries included”)
  • 타입 추론과 RPC 클라이언트 hc 제공
  • 활발한 릴리스 (4.13.x가 2026-10 ~ 11에 연속 릴리스)

단점

  • Node.js에서는 어댑터를 거치므로 Node 네이티브 프레임워크 대비 이점이 줄 수 있음 (fastify/benchmarks 2026-11-14: Hono 74,163, Fastify 78,696 req/s)
  • 5.0이 RC 단계이고 breaking change 예고: ESM only, 런타임 어댑터를 @hono/* 패키지로 분리, onError 시그니처 변경 등
  • 검증은 validator 미들웨어에 Zod 등 외부 라이브러리를 연동하는 방식
  • DI 같은 대규모 앱 구조화 기능은 제공하지 않음 (설계 철학상 최소)

적합한 상황 — 엣지/서버리스/멀티 런타임 배포, 가볍고 이식성 높은 API.

GitHub · honojs/hono 공식 문서 · hono.dev

Koa

Express 팀이 만든, 더 작고 표현력 높은 async 미들웨어 코어. 라우터와 바디 파서 등은 번들하지 않습니다.

최신 안정 3.3.0 (2026-11-03) 2.x 병행 (latest-2 2.16.4) stars 약 35.7k (2026-11-20)

핵심 특징

  • async 함수 기반, 콜백 제거로 에러 처리 개선
  • 코어에 미들웨어를 번들하지 않고, 미들웨어를 스택처럼 cascade (onion)
  • ctx(context)가 req/res를 감싸고 content negotiation, 캐시 freshness, redirect 같은 sugar 제공
  • 3.0: Node 18 이상, generator 지원 제거, WHATWG 응답 body 지원, app.currentContext(AsyncLocalStorage) 추가

장점

  • 코어가 작고(unpacked 약 66KB) 개념이 단순 (ctx + async 미들웨어)
  • onion 모델로 요청 전/후 처리를 하나의 함수에서 표현
  • 3.x에서 AsyncLocalStorage 기반 현재 context 접근 지원
  • Express 대비 에러 전파가 async/await 중심으로 일관됨
  • 필요한 것만 골라 붙이는 구성 자유도

단점

  • 라우터, 바디 파싱, 정적 서빙이 모두 별도 패키지라 조합과 선택 비용 발생
  • 내장 검증/스키마/OpenAPI 없음, 타입은 @types/koa 별도
  • 공개 벤치마크에서 Fastify, Hono보다 낮음 (fastify/benchmarks 2026-11-14: Koa 57,570 req/s, koa-router 포함 시 52,548)
  • 3.0 breaking change: ctx.throw 시그니처 변경, redirect('back') 제거, 특수 ENOENT 처리 제거 등

적합한 상황 — 프레임워크를 최소로 두고 미들웨어를 직접 조립하려는 소규모 서비스.

GitHub · koajs/koa 공식 문서 · koajs.com

Elysia

Bun에 최적화된 프레임워크. 엔드투엔드 타입 안전성과 인체공학적 API를 앞세웁니다.

최신 안정 1.4.32 (2026-11-11) 차기 2.0.0-rc.3 (pre-release) stars 약 19.4k (2026-11-20)

핵심 특징

  • 코드에서 타입을 자동 추론하고, Elysia.t(TypeBox 기반) 스키마가 런타임과 컴파일 타임의 단일 소스
  • Standard Schema 지원: Zod, Valibot, ArkType, Effect Schema, Yup, Joi 등
  • @elysia/openapi 플러그인으로 OpenAPI 적용, 타입에서 OpenAPI 생성도 지원
  • Eden Treaty(@elysia/eden)로 서버 타입을 코드 생성 없이 클라이언트에서 사용
  • WinterTC 준수. Bun, Node.js, Deno, Cloudflare Workers, Vercel 등에 배포 (Node는 @elysia/node 어댑터 필요)

장점

  • 라우트 → 스키마 → 클라이언트로 이어지는 엔드투엔드 타입 추론 (Eden)
  • 직접 의존성 4개 (cookie, exact-mirror, fast-decode-uri-component, memoirist)
  • Standard Schema 지원으로 검증 라이브러리 선택이 자유로움
  • lifecycle hook, macro, plugin으로 횡단 관심사 재사용
  • Bun 환경에서 상위권이라는 벤치마크를 공식 문서가 제시 (벤더 자체 주장)

단점

  • 생태계와 커뮤니티 규모가 작음 (stars 약 1.9만, npm 주간 약 220만으로 여섯 중 최저)
  • 최고 성능과 기능은 Bun 전제. Node에서는 어댑터를 거치며, fastify/benchmarks(Node, 2026-11-14)에서 68,231 req/s로 Fastify, Hono보다 낮음
  • 2.0이 beta/rc 단계이고 “전체 재작성”이라 1.x 사용자는 이행 비용이 생길 수 있음
  • peerDependencies에 @types/bun, @sinclair/typebox, openapi-types 등이 있어 구성이 Bun 중심

적합한 상황 — Bun 기반 신규 프로젝트, 프런트와 타입을 공유하는 풀스택 TypeScript.

GitHub · elysiajs/elysia 공식 문서 · elysiajs.com

NestJS

모듈, DI, 데코레이터로 서버 앱을 구조화하는 TypeScript 프레임워크. 내부 HTTP 서버는 Express(기본) 또는 Fastify입니다.

최신 안정 12.5.1 (2026-11-16, @nestjs/core) 11.x 병행 (legacy 11.2.11) stars 약 77.1k (2026-11-20)

핵심 특징

  • 모듈, 의존성 주입, 데코레이터, 마이크로서비스 지원
  • HTTP 어댑터: Express(기본), 선택적으로 Fastify 또는 node:http
  • v12(2026-08-27): ESM 패키지, Standard Schema 검증/직렬화, CLI 재작성, @nestjs/observe
  • v12는 Node.js 20.19+ 또는 22.12+ 필요
  • v11(2025-01-16): Express v5, Fastify v5로 업그레이드, Node 16/18 지원 중단

장점

  • 구조(모듈/DI/Guard/Pipe/Interceptor)가 정해져 있어 대규모, 다인원 팀에서 일관성 확보
  • 마이크로서비스, WebSocket, GraphQL 등 확장 패키지를 공식 제공
  • 어댑터 방식이라 Express ↔ Fastify 전환 가능
  • 12.x에서 Standard Schema 지원으로 Zod, Valibot, ArkType 사용 가능 (class-validator도 계속 지원)

단점

  • 하부 어댑터 위의 추상화 레이어라 순수 프레임워크 대비 오버헤드와 학습 곡선이 있음
  • 데코레이터 + reflect-metadata 의존, 요구하는 Node 버전이 높음
  • 메이저가 빠르게 바뀜: 11.0.0(2025-01) → 12.0.0(2026-08), 11 계열은 legacy 태그로 이동
  • Web 표준/엣지 런타임 직접 지원은 목표가 아님 (Node.js 기반)

적합한 상황 — 엔터프라이즈 백엔드, 여러 팀이 같은 구조를 공유해야 하는 대규모 서비스.

03 · 실측벤치마크

이 머신 한 대에서 잰 단순 hello-world 급 측정입니다. 프레임워크가 요청 하나에 얹는 오버헤드만 보여 주며, 실제 서비스 성능은 DB와 비즈니스 로직이 지배합니다. 순위를 그대로 서비스 성능으로 읽지 마세요.

oha로 loopback(127.0.0.1)의 서버 프로세스 하나에 부하를 걸었습니다. 서버마다 같은 8개 라우트를 등록하고, 응답 본문과 상태 코드가 기대값과 같은지 확인한 뒤, 시나리오마다 2초 워밍업 후 본 측정을 했습니다. 조합은 하나씩 차례로 실행했고 NODE_ENV=production으로 띄웠습니다. Fastify는 응답 스키마 없이, Koa는 @koa/router와 함께, Node.js의 Hono는 @hono/node-server로 측정했습니다. node:http와 Bun.serve는 프레임워크 없이 런타임 내장 서버만 쓴 기준선입니다.

NestJS는 실측 대상이 아닙니다. Express 또는 Fastify 어댑터 위에서 동작하는 구조라 이번 측정 스크립트에는 넣지 않았습니다.

results.json 을 불러오는 중입니다.

    05 · 정리선택 가이드

    이런 상황이면 후보 이유
    레퍼런스와 인력 수급, 생태계 호환이 우선인 일반 Node.js 서버 Express 생태계와 레퍼런스가 가장 풍부한 표준 선택지
    Node.js에서 스키마 기반의 고성능 REST API Fastify 검증·직렬화·타입을 스키마 하나로 연결, 플러그인 캡슐화
    엣지, 서버리스, 여러 런타임에 같은 코드를 배포 Hono Web 표준만 사용, 의존성 0, 작은 번들
    프레임워크를 최소로 두고 미들웨어를 직접 조립 Koa 미니멀 코어 + async onion 미들웨어
    Bun 기반 신규 프로젝트, 프런트와 타입 공유 Elysia Bun 최적화, 엔드투엔드 타입 추론과 Eden 클라이언트
    여러 팀이 같은 구조를 공유하는 대규모/엔터프라이즈 백엔드 NestJS 모듈 + DI + 데코레이터로 정해진 구조

    Fastify 6, Hono 5, Elysia 2가 pre-release 단계이고 Hono 5와 Elysia 2는 breaking change를 예고했습니다. 새로 도입한다면 각 마이그레이션 가이드를 함께 확인하세요.
