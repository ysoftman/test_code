측정 방식 및 재현 (Methodology)

  • 코퍼스: three.js r108 src(ES 모듈 370개)를 사본으로 복제하고, entry 가 사본마다 import * as copyN 한 namespace 를 전역 배열에 담습니다. 모든 코드가 쓰이므로 tree-shaking 으로 빠지는 코드가 없습니다.
  • 같은 출력: 모든 번들러가 minify + 외부 sourcemap 으로 파일 하나를 만듭니다. Rollup 은 minifier 가 없어 @rollup/plugin-terser 를 붙이고, webpack · Rspack 은 mode: "production" 기본 minifier 를 씁니다. Vite 는 JS entry 하나를 묶는 lib 모드(iife)에 기본 minifier(Oxc)를 씁니다. 캐시는 쓰지 않습니다.
  • 검증: 측정 전에 각 번들을 node 로 실행해 사본 수만큼 three.js 가 들어 있는지(REVISION), sourcemap 파일이 있는지 확인합니다.
  • 재현 명령: bun run bench:bundler 실행 시 벤치마크가 재수행되고 bundler-results.json이 업데이트됩니다.

결과 해석 (Engineering Notes)

  • 네이티브 vs JS: esbuild(Go) · bun build(Rust, v1.4.0+) · Rolldown · Rspack(Rust)은 파싱 · 링크 · minify 를 네이티브 코드로 병렬 처리합니다. Rollup · webpack 은 번들링과 minify 가 모두 JS 라 시간이 10배 이상, 메모리가 GB 단위로 듭니다.
  • minify 비중: Rollup · webpack 시간의 대부분은 terser 입니다. ×10 에서 minify 를 끄면 Rollup 은 약 5 s, webpack 은 약 3 s 로 줄어듭니다(별도 3회 측정).
  • Rspack vs webpack: 같은 설정 파일을 그대로 쓰지만, Rust 코어와 SWC minifier 덕분에 webpack 보다 열 배 안팎 빠릅니다.
  • Vite vs Rolldown: Vite 8 은 같은 Rolldown 과 Oxc minifier 로 번들링하고, 그 위에 설정 해석 · 플러그인 파이프라인 · gzip 크기 보고가 더해져 Rolldown 단독보다 조금 느립니다. gzip 크기 보고(reportCompressedSize)를 끄면 ×10 에서 약 60 ms 줄어듭니다(별도 5회 측정).
  • 고정 비용: Rolldown · Vite · Rspack 은 Node.js 위에서 CLI 와 설정을 읽고 Rust 코어를 napi 로 부르는 구조라, 단일 네이티브 바이너리인 esbuild · bun 보다 기동 비용이 커서 작은 입력에서 차이가 더 벌어집니다.
  • 결과물 크기: gzip 기준 차이는 몇 % 안쪽입니다. terser · SWC · Oxc 가 조금 더 작고, 속도를 우선하는 esbuild · bun 이 조금 더 큽니다.
