코퍼스별 결과 (Corpora)

hyperfine 으로 러너 프로세스 시작부터 종료까지 잰 값입니다. 실행 시간은 벽시계 평균, CPU 시간은 워커를 포함한 모든 자식 프로세스의 user + sys 평균입니다. 바 길이가 짧을수록 좋으며, 상대 배수는 해당 코퍼스의 최솟값 기준입니다. 빗금 바는 병렬 옵션을 켠 결과입니다.

측정 환경 및 기술적 분석

측정 방식 및 재현 (Methodology)

  • 코퍼스: 테스트 파일마다 같은 내용의 src/mNNN.ts 모듈을 하나씩 import 하고, 덧셈 · 문자열 · 깊은 비교(toEqual) · 비동기 (resolves) · 예외(toThrow) 테스트를 돌아가며 담습니다. 파일 1개와 스위트 두 가지 크기로 잽니다.
  • 같은 테스트: 각 러너 자체의 expect 를 씁니다. Bun · Vitest 는 자체 모듈에서 import 하고, Jest 는 전역 주입, Deno 는 node:test 와 jsr:@std/expect 입니다. 자체 expect 가 없는 Node.js 만 node:test 와 Jest 의 npm expect 를 씁니다.
  • 설정: 러너 기본값을 그대로 씁니다. Jest 는 TS 를 직접 읽지 못해 @swc/jest 변환을 붙이고, Deno 는 다른 러너처럼 타입 검사를 건너뛰도록 --no-check 를 줍니다. 파일을 직렬로 도는 Deno · Bun 은 --parallel 도 함께 잽니다.
  • 검증: 측정 전에 각 러너를 한 번 돌려, 출력의 통과 수가 전체 테스트 수와 같을 때만 측정합니다. 측정 중에도 실패하면 hyperfine 이 중단됩니다.
  • 재현 명령: bun run bench:test 실행 시 벤치마크가 재수행되고 test-results.json이 업데이트됩니다.

결과 해석 (Engineering Notes)

  • 파일 격리 비용: Bun 은 기본으로 모든 테스트 파일을 한 프로세스 · 한 전역에서 직렬로 실행해 파일당 고정 비용이 거의 없습니다. Vitest(파일마다 격리된 모듈 그래프), node --test(파일마다 프로세스), Deno(모듈마다 새 isolate)는 파일 수에 비례하는 고정 비용을 냅니다. 격리를 끄면 (vitest --no-isolate, node --test --test-isolation=none) 이 스위트가 0.6 ~ 0.8 s 로 줄지만(별도 3회 측정), 파일 사이에 전역 상태가 공유됩니다.
  • 병렬 실행: Jest · Vitest · node --test 는 기본으로 워커를 병렬로 돌려 CPU 시간이 벽시계 시간보다 훨씬 큽니다. Deno 는 --parallel 로 크게 빨라지지만, Bun 은 --parallel 이 격리(--isolate)를 켜고 워커를 띄우는 비용이 더 커서 이 규모에서는 오히려 느립니다. 파일당 테스트가 무거울 때 이득입니다.
  • Jest vs Vitest: 이 스위트에서는 Jest 가 더 빠릅니다. Jest 는 @swc/jest 변환 결과를 디스크에 캐시해 워밍업 뒤에는 변환을 건너뛰고, Vitest 는 실행마다 변환하면서 파일마다 격리된 환경을 새로 만듭니다.
  • 시작 오버헤드: 파일 1개 결과는 대부분 러너 자체를 띄우는 비용입니다. Node.js 위에서 도는 Jest · Vitest 는 러너 모듈 로딩에 수백 ms 의 CPU 를 쓰고, Bun 은 10 ms 안팎입니다. 측정 머신은 프로세스 기동마다 약 20 ms 가 붙고 흔들려서, 50 ms 미만 값은 편차가 크니 순위 위주로 보세요.
